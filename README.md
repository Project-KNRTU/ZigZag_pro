# ZigZag

ZigZag — мини-приложение для MAX, которое помогает пользователю находить интересные места и события в Казани, формировать маршрут и переходить на бронирование афиши.

Проект состоит из клиентского интерфейса, Node.js-сервера на Express, интеграций с внешними API и модуля хранения пользовательских маршрутов. Для сохранения и доступа к маршрутам используется авторизация через подтверждённые данные пользователя MAX.

## Назначение решения

ZigZag решает задачу планирования прогулки или поездки по городу:

- пользователь выбирает интересующие категории мест;
- приложение получает реальные места из 2GIS Search API;
- пользователь указывает дату и получает события из афиши KudaGo;
- пользователь формирует маршрут из выбранных точек.

Основной город в текущей MVP-версии — Казань.

## Основной пользовательский сценарий

1. Пользователь открывает мини-приложение ZigZag внутри MAX.
2. MAX передаёт в приложение данные текущего пользователя (`initData`).
3. Пользователь выбирает категории интересующих мест.
4. Клиентская часть запрашивает места через API ZigZag.
5. Сервер получает актуальные места через 2GIS Search API и передаёт их клиенту.
6. Пользователь выбирает дату посещения.
7. Клиент запрашивает события на выбранную дату.
8. Сервер получает афишу через KudaGo и возвращает список доступных событий.
9. Пользователь выбирает точки и формирует маршрут на карте.
10. Сервер проверяет подпись данных MAX, определяет реальный `user.id` и сохраняет маршрут именно за этим пользователем.

### Принцип защиты маршрутов

Все маршруты `/api/routes` защищены middleware `requireMaxUser`.

Middleware выполняет следующие действия:

1. Получает заголовок `X-Max-Init-Data`.
2. Проверяет подпись данных, полученных от MAX.
3. Извлекает подтверждённый идентификатор пользователя MAX.
4. Записывает идентификатор в `request.maxUserId`.
5. Передаёт управление обработчику маршрута.

Идентификатор пользователя не принимается из `request.body`, параметров URL или клиентского JavaScript. Это предотвращает доступ одного пользователя к маршрутам другого пользователя.

## API приложения

API ZigZag состоит из публичных и защищённых маршрутов.

Публичные маршруты не требуют авторизации в MAX. Они используются для проверки работы сервера, получения настроек карт, поиска мест и загрузки событий.

Защищённые маршруты предназначены для работы с сохранёнными маршрутами пользователя. Для обращения к ним требуется авторизация MAX. Сервер получает и проверяет данные пользователя из заголовка X-Max-Init-Data, после чего определяет текущего пользователя и разрешает работать только с его маршрутами.

GET /api/health — проверяет работоспособность сервера ZigZag. Авторизация MAX не требуется.

GET /api/config — возвращает публичную конфигурацию карт, включая ключ для 2GIS MapGL и ключ для сервиса построения маршрутов. Авторизация MAX не требуется.

GET /api/places?categories=... — получает реальные места по переданным категориям. Категории указываются в параметре categories через запятую, например: кафе,музеи,парки. Авторизация MAX не требуется.

GET /api/events?date=YYYY-MM-DD — возвращает список событий на указанную дату. Дата передаётся в параметре date в формате YYYY-MM-DD, например 2026-09-29. Авторизация MAX не требуется.

GET /api/routes — возвращает список сохранённых маршрутов текущего пользователя. Требуется авторизация MAX. Пользователь получает только маршруты, которые были сохранены в его аккаунте.

GET /api/routes/:id — возвращает один сохранённый маршрут по его идентификатору. Требуется авторизация MAX. Сервер дополнительно проверяет, что запрошенный маршрут принадлежит текущему пользователю.

POST /api/routes — сохраняет новый маршрут текущего пользователя. Требуется авторизация MAX. Данные маршрута передаются в теле запроса, при этом идентификатор пользователя не передаётся клиентом и определяется сервером после проверки данных MAX.

DELETE /api/routes/:id — удаляет сохранённый маршрут по его идентификатору. Требуется авторизация MAX. Удалить можно только маршрут, принадлежащий текущему пользователю.

## Внешние сервисы и интеграции

### MAX

MAX используется для запуска мини-приложения и идентификации пользователя.

Назначение интеграции:

- передача данных авторизованного пользователя в мини-приложение;
- передача `X-Max-Init-Data` на сервер;
- проверка подлинности пользователя перед работой с маршрутами;
- привязка сохранённых маршрутов к настоящему `user.id`.

Условия для проверки:

- мини-приложение должно быть зарегистрировано и доступно в MAX;
- сервер приложения должен быть доступен по публичному HTTPS-адресу;
- в `max-auth.js` должны быть настроены корректные параметры проверки подписи;
- клиентская часть должна передавать полученные от MAX данные в заголовке `X-Max-Init-Data`.

Контейнеризация не заменяет работу приложения внутри MAX. Docker используется для локального запуска и разработки, но основной пользовательский сценарий должен оставаться доступен из MAX.

### 2GIS MapGL

2GIS MapGL используется для отображения карты в клиентской части приложения.

Для работы требуется:

- действующий ключ `MAPGL_KEY`;
- доступ клиента к ресурсам 2GIS;
- подключение JavaScript SDK карты в клиентской части.

### 2GIS Directions API

2GIS Directions API используется для построения маршрута между выбранными точками.

Для работы требуется:

- действующий ключ `DIRECTIONS_KEY`;
- доступ в интернет;
- корректные координаты выбранных точек маршрута.

### 2GIS Search API

2GIS Search API используется для поиска реальных мест по выбранным пользователем категориям.

Серверный endpoint:

GET /api/places?categories=кафе,музеи,парки


Пример ожидаемого ответа:

json
{
  "success": true,
  "source": "2GIS Search API",
  "count": 2,
  "places": [
    {
      "name": "Пример места",
      "category": "Кафе"
    }
  ]
}


### KudaGo

KudaGo используется для получения событий и афиши.

Серверный endpoint:

GET /api/events?date=2026-09-29

Параметр `date` обязателен и должен соответствовать формату `YYYY-MM-DD`.

При некорректной дате сервер вернёт:

json
{
  "success": false,
  "error": "Передайте параметр date в формате YYYY-MM-DD."
}


## Работа с данными

### Места и события

Данные о местах и событиях не являются постоянными данными ZigZag.

- места запрашиваются у 2GIS Search API в момент обращения к `/api/places`;
- события запрашиваются у KudaGo в момент обращения к `/api/events`;
- сервер возвращает клиенту актуальные данные внешних сервисов;
- при недоступности внешнего API сервер возвращает ошибку `500`.

### Маршруты пользователей

Маршруты являются пользовательскими данными и обрабатываются через `database.js`.

Для каждого маршрута важно:

- маршрут сохраняется только для пользователя, прошедшего проверку MAX;
- идентификатор пользователя берётся только из `request.maxUserId`;
- маршрут нельзя получить по ID, если он принадлежит другому пользователю;
- маршрут нельзя удалить, если он принадлежит другому пользователю;
- пустой массив точек маршрута не сохраняется.

Пример минимального тела запроса на сохранение маршрута:

json
{
  "title": "Прогулка по Казани",
  "date": "2026-09-29",
  "route": [
    {
      "name": "Точка отправления",
      "coordinates": [49.1064, 55.7961]
    },
    {
      "name": "Точка назначения",
      "coordinates": [49.1221, 55.7887]
    }
  ]
}


Пример успешного ответа:

json
{
  "success": true,
  "message": "Маршрут сохранён.",
  "id": 1
}


## Работа с тестовыми данными

### Тестирование публичной части

Публичные endpoints можно проверить локально без MAX-авторизации.

Проверка состояния сервера:

curl http://localhost:3000/api/health


Проверка получения мест:


curl "http://localhost:3000/api/places?categories=кафе,парки"


Проверка событий:

curl "http://localhost:3000/api/events?date=2026-09-29"


Для этих запросов нужны настроенные внешние сервисы и доступ в интернет.

### Тестирование маршрутов

Endpoints маршрутов требуют настоящий и корректно подписанный заголовок `X-Max-Init-Data`.

Пример структуры запроса:

curl \
  -H "X-Max-Init-Data: <данные_инициализации_MAX>" \
  http://localhost:3000/api/routes


Для полноценной проверки защищённых маршрутов необходимо открыть приложение из MAX, чтобы платформа передала настоящие данные текущего пользователя.

Не рекомендуется вручную подставлять или подделывать `X-Max-Init-Data`: сервер должен принимать только данные, прошедшие криптографическую проверку в `max-auth.js`.

## Пошаговая проверка

1. Создайте `.env` и укажите ключи 2GIS.
2. Добавьте переменные, необходимые для работы `max-auth.js`.
3. Запустите приложение:

```bash
docker compose up --build
```

4. Проверьте доступность сервера:

```bash
curl http://localhost:3000/api/health
```

5. Откройте локальную страницу приложения:

```text
http://localhost:3000
```

6. Проверьте получение конфигурации карты:

```text
http://localhost:3000/api/config
```

7. Выберите одну или несколько категорий мест и убедитесь, что клиент получает данные из `/api/places`.
8. Укажите дату в формате `YYYY-MM-DD` и убедитесь, что клиент получает данные из `/api/events`.
9. Выберите несколько точек на карте и сформируйте маршрут.
10. Откройте приложение внутри MAX.
11. Убедитесь, что клиент передаёт `X-Max-Init-Data` при обращении к `/api/routes`.
12. Сохраните маршрут.
13. Откройте список сохранённых маршрутов и убедитесь, что новый маршрут отображается.
14. Откройте сохранённый маршрут по его идентификатору.
15. Удалите маршрут.
16. Убедитесь, что удалённый маршрут больше не возвращается в списке.
17. Проверьте, что другой пользователь MAX не может получить или удалить маршрут первого пользователя.

## Известные ограничения

- Текущая MVP-версия ориентирована на Казань.
- Получение мест зависит от доступности 2GIS Search API.
- Отображение карты и построение маршрута зависят от ключей 2GIS и внешней сетевой доступности.
- Получение событий зависит от доступности и актуальности данных KudaGo.
- Полноценная проверка пользовательских маршрутов требует запуска мини-приложения внутри MAX.
- Локальный запуск через `localhost` подходит для проверки публичной части, но не заменяет доступное по HTTPS мини-приложение MAX.
- При недоступности внешнего API приложение не сможет получить новые места или события.
- Доступные функции хранения маршрутов зависят от реализации `database.js` и настроенного хранилища данных.
- Статические файлы временно раздаются из корня проекта через `express.static(__dirname)`. В дальнейшем рекомендуется перенести клиентские файлы в каталог `public/`.
